# Debloat checks

Shared by `debloat-scan` (whole project) and `debloat-file` (one file). Every check reports its estimated token cost using the same tokens-per-word approximation: `words * 1.3`, rounded, and states it as an estimate, not an exact count. Where the real number matters, defer to a `/context` reading instead of the estimate.

Every finding must name the file and line, the problem in one line, and the concrete fix. Group findings under **Reduces the always-loaded footprint**, **Redundant or duplicated**, **Signal quality**, and **Structural**, most token-impact first. Report a headline number before the findings: total estimated always-loaded tokens across the whole surface, and that as a percentage of a 200k reference window. Do not invent a 0-100 score, the headline is the token estimate itself.

## Reduces the always-loaded footprint

**Line and size caps.** A CLAUDE.md, rules file, or any always-loaded file over roughly 200 lines or 25KB is a candidate for trimming or splitting, this threshold comes from Anthropic's own documented guidance and matches what other tools in this space use independently. Flag it, do not assume it is wrong on its own, some content genuinely needs that length.

**Unconditional `@`-imports of content that is not universally needed.** `@`-imports load in full, unconditionally, at launch, regardless of whether the current task touches that content. If an imported file is domain-specific (styling, a particular framework, a particular language) rather than genuinely relevant to every single task, it is a candidate for converting into a path-scoped `.claude/rules/*.md` file with `paths:` frontmatter instead, which only loads when a matching file is touched. Do not flag an import of content that is genuinely needed on every task (project overview, core conventions), that is what imports are for.

**Circular `@`-imports.** Walk the import graph from each CLAUDE.md: file A imports file B imports file A (or a longer cycle). This wastes nothing by itself (Claude Code presumably resolves it safely) but signals a structural mistake worth fixing, and is cheap to detect: build the graph, check for cycles.

**An unselective `paths:` glob in a rules file** (for example `paths: ["**/*"]` or `paths: ["*"]`). This behaves exactly like an always-loaded file despite living in the mechanism meant to load conditionally. Flag it and suggest a narrower glob matching the file's actual subject.

**A custom agent's prompt that duplicates CLAUDE.md content wholesale instead of referencing it.** This does not cost anything in the parent session (agents only load their full body in their own isolated context window when invoked), but it does mean that isolated window carries redundant content every time the agent runs. Flag it as a finding, note explicitly that its cost is invisible to a parent-session `/context` reading and only shows up when the agent is actually used.

## Redundant or duplicated

**The same instruction, substantively repeated across two or more files** (CLAUDE.md, a rules file, an agent prompt, a command, or a docs file the surface points at). Near-verbatim repetition, not just a shared theme, but "near-verbatim" includes reworded restatement, not only identical strings: the same list of items in the same order, the same procedure steps in the same sequence, or the same qualifier attached to the same rule, is duplication even when barely a single sentence matches word for word. If two files independently explain the same convention from a genuinely different angle (a build-time rule versus the reasoning for why it exists) that is not automatically redundant. Flag each duplicate location, suggest keeping the fullest version in the most-loaded-by-default location and having the others reference it instead.

**Do not conclude "no duplication" from one top-to-bottom read of each file.** Paraphrased duplication is easy to miss this way, because the two copies are rarely adjacent and rarely worded alike. Before writing findings for this section, do a second, deliberate pass keyed by *topic* rather than by file: list every distinct instruction, procedure, or fixed set of items found anywhere in the surface (a colour-layering rule, a review procedure, a boilerplate checklist, a "run X before done" requirement), then check that topic's wording against every other file, not only the ones read next to each other. A convention that recurs three or more times across build-rule files, rules files, and any spec/checklist file is common in a project with several tiers of documentation, and is exactly what this check exists to catch, so treat a clean-looking first pass as a reason to look harder, not as a result to report.

**A file that cites another file as authoritative and then restates its content anyway.** This is the most common way real duplication hides. A rules file, agent prompt, or command says something like "see `docs/X` for the full procedure" or "`X` is the spec, read it in full and apply it exactly," and then goes on to reproduce that procedure, format, or list in its own body in comparable detail, just paraphrased. The citation reads as good practice and makes what follows easy to skim past, but citing the canonical source does not cancel restating it, it just proves the author already knew where the canonical version lived. Treat any file with this shape as a priority check: pull in the cited file even if it is a plain `docs/*.md` never `@`-imported (it belongs in the duplication-check surface, alongside the standard enumeration, whenever some rule, agent, or command instructs reading it every time that item runs) and diff its sections against the citing file's own body, section by section. This case costs more than ordinary duplication when the citing file is an agent or command: the agent pays the full token cost of reading the cited file, per its own instruction, on every invocation, *and* carries its own restated copy permanently in its prompt, so the waste compounds rather than merely doubling.

## Signal quality

**Emphasis-word overuse.** Anthropic's own guidance confirms emphasis (IMPORTANT, YOU MUST, CRITICAL) measurably tunes adherence, but their model-specific guidance for newer models also warns this can overtrigger when overused, and using it on nearly every line dilutes it back down to no signal at all. Flag a file where most lines carry emphasis markers, since that is a sign none of them are actually being treated as more important than the rest. This is a quality finding, not a token-count one, report it separately from the always-loaded-footprint findings.

## Structural (file-level, for `debloat-file` especially)

**An oversized SKILL.md with no sibling reference files, scripts, or assets.** Real Claude Code skills push detail into `references/*.md` (linked inline from the body) or `scripts/*` once the body would otherwise run long or cover more than one distinct concern. Judge this on estimated tokens and distinct-concern count together, not raw line count, a prose-paragraph body can pack several hundred words into fifty short-looking lines. As a rough guide: a body estimated over roughly 600-700 tokens *and* covering more than two or three genuinely independent concerns (each a candidate for its own reference file) is a real violation, not a near-miss. A shorter body, or one covering a single concern in depth, is fine at any line count, depth on one topic is what a skill body is for.

**A SKILL.md description that is narrative rather than trigger-shaped, or near the 1024-character cap.** The description is the only thing loaded at rest and the only signal Claude has for choosing this skill over another. It should read as: what it does, in one sentence, then "Use when [specific, concrete triggers]." A long, story-like description wastes always-loaded tokens without actually improving triggering, and a description near the character cap is worth double-checking for the same reason a long always-loaded file is.

**Reference material that doesn't follow the `references/` colocation convention.** Claude Code's own skill format uses `.claude/skills/<name>/references/*.md` for supporting material a skill loads progressively instead of inlining it into `SKILL.md`. Apply the same shape everywhere: material specific to one rule, agent, skill, or command belongs colocated next to it as `.claude/<type>/<name>/references/*.md` — a plain sibling folder the item's own file points to by relative path (agents and rules are discovered recursively by frontmatter/glob rather than by exact filename, so the item's own file can stay flat with just a same-named `references/` folder added beside it; it does not need to move into a nested `<name>/<name>.md` itself). General "good to know" material that isn't owned by any single rule/agent/skill/command belongs in one root-level `references/*.md` folder instead of a generically-named one.

A generically-named top-level folder (`docs/`, `notes/`, etc.) is not itself a problem: plenty of projects legitimately keep human-facing docs or notes there, untouched by Claude Code's loading mechanism, and that's fine as is. Only raise it, and only as a soft flag rather than a firm violation, when the folder's actual contents are really a CLAUDE.md extension in disguise: instructions written for Claude rather than for human readers, that some rule or agent depends on. The clearest tell is the material's own text saying something like "this is the spec for the X agent" while it sits somewhere no rule or agent points at exclusively. When that's the case, suggest renaming the folder to `references/` (or colocating it with the owning item) rather than treating the generic name as a defect on its own. A root-level reference folder not named `references/` that already holds Claude-facing material, or a rule/agent/command file that has grown a long reference-shaped section inline (an exhaustive table, a large worked-example block), are both worth the same soft mention. This is a file-organization observation, not a token-load finding by itself, Claude Code doesn't auto-load `references/*.md` outside a skill, but poor colocation is usually what leads to the token findings above: material that should be scoped to one rule or agent ends up in a shared folder that then either gets swept into an unconditional `@`-import, or has its ownership go unclear and gets duplicated instead of referenced.
